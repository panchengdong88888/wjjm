# 检查点 #32：DiuItems 原始元组与分支判定复核

日期：2026-11-09  
对象：`root.children[46]` / legacy `root/47` / `DiuItems`

## 本轮直接从 VM dump 复核的事实

1. DiuItems 原型原始记录数 169，常量数 64，子原型数 1。
2. root 创建指令为 `[0,27,8,46,2]`；后续两个捕获描述分别为 `[192,387,0,2,0]` 与 `[128,387,0,5,0]`。因此 UP[0]/UP[1] 分别捕获父 root 的 T[2]/T[5]。
3. 子闭包创建指令捕获 DiuItems 的 T[5]；子闭包本体执行 `ipairs` 遍历关键词，并调用 `string.find(name, keyword, 1, true)`。命中时返回 true，遍历结束返回 false。
4. 原始元组中 PC89 对应记录（0-based raw index 88）为 `[224,92,1,4,1]`，即 OP_092，操作数 A=1、B=4、C=1。
5. opcode 参考定义 OP_092 的条件为：
   `if (R[B] == C) ~= (A ~= 0) then Q = Q + 1 end`
   因此该处精确条件是 `(R[4] == 1) ~= true`；当 R4 等于 1 时不跳过下一条指令，当 R4 不等于 1 时跳过下一条指令。
6. 在可见的顶层原始元组中，R4 相关写入出现在：
   - raw index 16：字符串拼接结果写入 R4（超上限提示文本）；
   - raw index 21：拼接结果写入 R4；
   - raw index 32–33：复位共享状态表字段；
   - raw index 35：OP_299，A=4、B=1，且标注有 6 个线性融合载荷。
   - 从 raw index 36 到 88 的显式记录中，没有一条普通记录以 A=4 写入 R4。
7. 这并不足以直接断言 PC89 的 R4 必然为 1：raw index 35 的 OP_299 带 6 个融合载荷，必须依照解释器实际取指/载荷消费方式确定融合链内每一条写入的目标寄存器及顺序，不能把反汇编展示行简单视为独立执行指令。

## LuaSendMsg 调用链的元组边界

原始元组中：
- raw index 142（反汇编 PC143）是 OP_349，A=14、B=`LuaSendMsg`，标注 11 个线性融合载荷；
- raw index 143–154 连续构造 global.MsgType.MSG_CS_MAP_ITEM_DISCARD、候选项 makeIndex/count/name、string.len(name) 等表达式；
- raw index 155（反汇编 PC156）是 OP_013，调用 R14 的开放参数区。

这证明了协议常量与候选字段的来源，但由于 OP_349 的融合载荷与 T 区开放参数边界尚未逐项解开，目前不把参数顺序、隐式接收者或附加协议字段写成已证实结论。

## 重要纠正与未决项

- PC89 是条件比较，不是简单的“关键词命中”布尔值；它依赖 R4 的运行时值。
- PC91–98 的候选插入分支是否可达，必须先解决 PC35 的 OP_299 融合链。
- LuaSendMsg 的实际实参表仍需从 OP_349 融合链、T 区赋值和 OP_013 开放参数调用共同恢复。
- PC128–160 的迭代器、35 件计数边界仍需结合循环控制流继续核对。
