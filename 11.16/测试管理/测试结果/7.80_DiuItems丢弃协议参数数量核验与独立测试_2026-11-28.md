# 7.80：DiuItems 丢弃协议参数数量核验与独立测试

日期：2026-11-28  
状态：**测试版已创建，等待用户实机验证；唯一正式版未修改。**

## 1. 7.79 实机错误

用户在首次点击“开丢全部”时提供截图，错误定位为：

- 点击入口：`dropallbut`
- 功能回调：`DiuItems`
- 出错位置：`GUILayout/MainLeftBottom.lua:2605`
- 引擎异常：`LuaNetworkController:SendMsg` 参数数量不正确，收到 8 个参数。

功能回调抛错后，7.79 的通用点击包装器无法正常走完后续按钮状态更新。

## 2. 11.16 原始证据核对

### 当前 11.16 原版及提取记录

- 原版加密文件：`11.16/MainLeftBottom 11.16原版.lua`
  - Git blob SHA：`ceadad470b2f73e82e8ff90d0d6417816058adaa`
- 当前明文恢复文件：`11.16/MainLeftBottom_11.16_明文.lua`
  - Git blob SHA：`7b90e8b89389727fd709bae36a71d6996b8ff898`
- 原型提取记录：`11.16/候选原型完整指令提取.json`
  - Git blob SHA：`9bf533c78f577f7559b6d8f0e01ebafd1c7d6e4c`

提取记录中 `root/2` 为 226 条指令。丢弃协议调用附近的槽位 200–213 显示：

- 槽位 200：取得 `LuaSendMsg`
- 槽位 201–203：取得 `global.MsgType.MSG_CS_MAP_ITEM_DISCARD`
- 槽位 204–208：准备 makeIndex、count、0、0、name
- 槽位 209–210：取得 `string.len` 并计算名称长度
- 槽位 211：再次取得候选记录的 `name`
- 槽位 212：将该值继续放入调用参数寄存器
- 槽位 213：执行调用

因此，当前 11.16 提取记录确实反映出 8 个调用参数（包含消息类型）；不能声称第 8 项是恢复代码时凭空添加的。当前明文中的 8 参数调用与这份提取记录相符。

### 旧版对照

旧版整合文件 `11.16/MainLeftBottom 11.2+11.9 整合.lua` 的同一协议调用只有 7 个总参数：

```lua
LuaSendMsg(
    global.MsgType.MSG_CS_MAP_ITEM_DISCARD,
    candidate.makeIndex,
    candidate.count,
    0,
    0,
    candidate.name,
    string.len(candidate.name)
)
```

旧版对照只能作为历史实现参考，不能替代 11.16 原始证据。

## 3. 本轮判断

1. 7.79 实机已经证实当前调用链把 8 个参数传到了 `global.networkCtl:SendMsg(...)`。
2. 引擎明确因参数数量报错；因此该调用在当前运行环境中不能正常完成。
3. 11.16 的当前原型提取结果与运行时 API 要求存在冲突：原始提取记录呈现 8 参数，但当前引擎接口拒绝 8 参数。
4. 本轮不篡改“原始恢复事实”：保留 11.16 原型提取记录中的 8 参数结论；另制作独立兼容性测试版，将末尾重复的 `candidate.name` 去掉，使实际发送变为 7 参数。
5. 这属于**待实机验证的运行兼容性修正**，不是宣称已经证明原始加密文件本身只有 7 参数。
