## 二、融合边界关键点

槽113执行Opcode55。原版F()中Opcode55不是普通单槽比较，而是融合执行链：从槽113开始，连续消费后续6条物理记录（槽114–119），循环尾再递增后从槽120继续。

因此：
- 槽114–119不能作为独立Opcode解释；
- 不能把槽114/116的Opcode388直接当作普通跳转；
- 槽117–119的Opcode174/110/60也不能独立解释为布尔赋值/条件跳过；
- 槽113–119的融合运算链仍需结合完整寄存器来源与原版执行效果进一步闭合。当前不把它简化成“金币低于100000”的普通比较，也不据此编写可执行修复。

槽120 Opcode388跳转目标128，按后置递增规则实际到槽129；但槽119在其他分支跳转入口下也可能被独立分派，因此必须分别核对不同入口路径，不能只按顺序直读。

## 更正补充：Opcode55并非融合块（2026-11-27）

前文“槽113 Opcode55融合消费后续6槽（槽114–119）”判断错误，现明确撤回。对原版F()分派树重新逐项定位后，Opcode55对应的执行体为：

```lua
if (N[K[3]] < K[4]) ~= (K[2] ~= 0) then
    O = O + 1
end
```

这是单槽条件跳过指令，不消费后续槽。槽113参数为`K[2]=0, K[3]=6, K[4]=100000`，故条件为`N[6] < 100000`，成立时跳过槽114，循环尾再递增一次，从槽115继续。

槽114与槽116的Opcode388均为跳转：
- 槽114：`O=116`，循环尾递增后从槽117执行。
- 槽116：`O=117`，循环尾递增后从槽118执行。

槽115 Opcode32对应：
```lua
if (N[K[3]] < K[4]) ~= (K[2] ~= 0) then
    O = O + 1
end
```
其参数为`N[7] < 100000`。槽115条件成立会跳过槽116，随后从槽117执行；条件不成立则执行槽116跳转，随后从槽118执行。

由此，槽113–119的实际分支可精确归纳为：
- 若`N[6] >= 100000`：槽113不跳过槽114，槽114跳转，下一步槽117。
- 若`N[6] < 100000`且`N[7] < 100000`：槽113跳过槽114，槽115再跳过槽116，下一步槽117。
- 若`N[6] < 100000`且`N[7] >= 100000`：槽113跳过槽114，槽115不跳过槽116，槽116跳转，下一步槽118。

因此，只有第三种情况会执行槽118；前两种情况从槽117执行。槽117 Opcode174的执行体为`N[K[2]]=K[3]~=0; if K[4]~=0 then O=O+1 end`，本槽参数使`N[4]=false`并跳过槽118，随后到槽119。第三种情况则槽118 Opcode110设置`N[4]=true`，随后到槽119。

槽119 Opcode60检查`(not not N[4]) ~= (K[4]~=0)`，本槽K[4]=0：
- N[4]=false时不跳过槽120，执行槽120跳转，下一步槽129；
- N[4]=true时跳过槽120，下一步槽121。

因此，槽121–128并非死代码，而是仅在`N[6] < 100000`且`N[7] >= 100000`时进入的隐藏状态处理路径。槽129–134为最终GUI:setVisible调用路径。槽121–128的完整隐藏状态布尔运算仍待进一步逐条闭合。

更正后的业务判断：原版金币警告不是单纯`gold < 100000 and not isHidden`。其进入隐藏状态处理路径还受第二个值`N[7]`（由`tonumber(SL:GetMetaValue("ITEM_COUNT", 3) or 0)`产生）是否达到100000影响。尚不能据此断言N[7]的业务含义，必须继续核验其来源与GUI参数的最终布尔值。


## 槽121–134隐藏状态分支的进一步闭合

基于原版F()对相关Opcode再次定位：

- Opcode234：`N[K[2]]=H[K[3]]`。槽121因此将`H[0]`读入N[5]。
- Opcode274：`N[K[2]]=N[K[3]][K[4]]`。槽122因此读取`N[5]["isHidden"]`。
- Opcode60：若`(not not N[K[2]]) ~= (K[4]~=0)`则跳过下一物理槽。槽123的K[4]=0，因此isHidden为真时跳过槽124；为假时执行槽124。
- Opcode315：若`(not not N[K[3]]) == (K[4]~=0)`则执行`N[K[2]]=N[K[3]]`，否则跳过下一物理槽。槽126的K[4]=1，故N[4]为真时将N[5]复制给N[4]；否则跳过槽127。
- Opcode110：`N[K[2]]=K[3]~=0`，若K[4]非0还会跳过下一槽。槽128将N[4]设置为false。

槽121–128两条路径：
1. isHidden为真：槽123跳过124；槽125把N[5]设为true；槽126在N[4]原为true的前提下将true复制到N[4]；槽127跳转至最终调用准备区。
2. isHidden为假：槽123执行槽124跳转到槽127，按后置递增实际进入槽128；槽128把N[4]设为false。

所以在前述第三种条件（N[6]<100000且N[7]>=100000）下，最终N[4]与`H[0].isHidden`一致：isHidden为真则true，为假则false。该方向看起来可能与字段名直觉相反，但这里只记录解释器真实数据流，不擅自改写成`not isHidden`。

槽129–134确实进入最终GUI可见性调用准备段：从全局表取GUI.setVisible，读取`H[0].goldWarnBg`，并将N[4]作为最终布尔寄存器之一传入调用。由于还需确认函数调用参数寄存器区间与槽129–134的完整调用约定，暂不把它表述为已完全闭合的源代码调用签名。

## 更新后的分支结论（仍需核实N[6]/N[7]数据含义）

- N[6]由MoneyProxy金币余额读取链产生。
- N[7]由`tonumber(SL:GetMetaValue("ITEM_COUNT", 3) or 0)`产生。
- N[6]>=100000：进入槽117路径，N[4]=false，随后跳到最终调用区。
- N[6]<100000且N[7]<100000：同样进入槽117路径，N[4]=false。
- N[6]<100000且N[7]>=100000：进入槽118及隐藏状态分支，最终N[4]等于`H[0].isHidden`。

这证明原版逻辑包含两种金币数值来源的交叉判断及隐藏状态处理，不能直接简化为正式版当前的`gold < 100000 and not isHidden`。N[7]对应的元数据ID=3究竟与MoneyProxy余额是否同一数值口径，仍需查框架API/原版业务语义证据；在此之前不进行实机测试或正式版修改。
