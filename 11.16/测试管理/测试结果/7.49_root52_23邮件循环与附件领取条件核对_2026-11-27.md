| 七项提取JSON字段 | 正确含义 |

原版 S() 每条指令是 K[1] 至 K[4] 四槽，不存在 K[5]。本记录以下所有槽位解释均使用上述正确映射。

## 二、原版F()相关Opcode语义

以下语义直接按原版 `F()` 分派器叶子和循环尾统一 `O=O+1` 还原：

- Opcode 96 / 410：`N[A]=N[B][C]`，普通表成员读取。
- Opcode 209：调用 `N[A](N[A+1]...N[B])`，单返回值写回 `N[A]`。
- Opcode 128 / 123：调用寄存器函数及参数区间，不接收返回值。
- Opcode 265：`N[A]=#N[B]`。
- Opcode 289：若 `(not not N[A]) ~= (K[4]~=0)`，内部跳过一槽，循环尾再加一，因此实际跳过下一物理槽。
- Opcode 326：若 `(K[3] < N[K[4]]) ~= (K[2]~=0)`，跳过下一物理槽。
- Opcode 143：若 `(N[K[3]] == K[4]) ~= (K[2]~=0)`，跳过下一物理槽。
- Opcode 110：`N[A]=(K[3]~=0)`。
- Opcode 340：真值与 K[4] 标志不相等时跳过下一物理槽。
- Opcode 357：泛型迭代器推进。调用 `N[A](N[A+1],N[A+2])`，将 C 个返回值写入 `N[A+3..A+2+C]`；首返回值为 nil 时跳过下一物理槽，否则把首返回值写入控制变量 `N[A+2]`。
- Opcode 388：设置 `O=K[3]`；由于循环尾还会统一加一，下一次实际执行目标槽位 `K[3]+1`。
- Opcode 361：本原型槽43的三槽融合链，消费后续槽44、45，完成全局 SL、GetMetaValue 方法及参数准备。

## 三、root/52/23 槽1–54控制流闭合

### 1. 邮件列表存在性与空列表检查（槽1–15）

- 槽1–3 Opcode361融合，准备 `SL:GetMetaValue("MAIL_LIST")`。
- 槽4 Opcode209执行调用，结果写入寄存器。
- 槽5 Opcode289检查列表是否存在。
- 槽6 Opcode388：列表不存在时跳至槽12。
- 槽7–9准备并调用全局 `next(MAIL_LIST)`。
- 槽10 Opcode366检查 `next` 的结果。
- 槽11 Opcode388：列表已有第一项时跳至槽16，进入邮件迭代。
- 槽12–14准备并调用 `SL:RequestMailList()`。
- 槽15 Opcode388：请求列表后跳过本轮邮件迭代，转至槽55之后的其他业务。

因此：MAIL_LIST 不存在或为空时才请求邮件列表；非空时不在该分支重复请求，而进入逐封检查。

### 2. pairs(MAIL_LIST) 初始化与迭代（槽16–38）

- 槽16初始化“是否找到可领取邮件”的布尔寄存器为 false。
- 槽17–19准备并调用 `pairs(MAIL_LIST)`，迭代器、表和控制变量写入寄存器2–4。
- 槽20 Opcode388 跳至槽35，实际下一执行槽为35；这是泛型 for 的首次迭代推进入口，不是跳过整个循环。
- 槽35 Opcode357 调用 pairs 迭代器，返回 key/value 到寄存器5、6；首返回值 nil 时跳过槽36，结束循环；有下一项时更新控制变量。
- 槽36 Opcode388 跳回槽21，实际下一执行槽为21。
- 槽21 Opcode289检查当前邮件对象寄存器6；对象为空时执行槽22跳转至下一次迭代，非空时继续。
- 槽23 Opcode96读取 `mail.sItem` 到寄存器7；槽24检查其真值。不存在时槽25跳到下一次迭代。
- 槽26 Opcode410再次读取 `mail.sItem`；槽27 Opcode265取其长度。
- 槽28 Opcode326判断 `0 < #mail.sItem`；长度为0时执行槽29跳到下一次迭代，长度大于0时跳过槽29。
- 槽30 Opcode410读取 `mail.btRecvFlag`。
- 槽31 Opcode143判断 `mail.btRecvFlag == 0`；不等于0时执行槽32跳到下一次迭代；等于0时跳过槽32。
- 槽33 Opcode110将“找到可领取邮件”标志置为 true。
- 槽34 Opcode388跳至槽37之后，离开邮件迭代体；因此找到第一封符合条件的邮件后，不再继续扫描其余邮件。

由此闭合的自动领取候选条件为：邮件对象存在、`sItem` 为真值且长度大于0、`btRecvFlag == 0`。该判断是原型寄存器/分支语义，不对字段在服务端的更深层含义作额外推断。

### 3. 自动领取与删除已读邮件分支（槽37–54）

- 槽37 Opcode340检查“找到可领取邮件”标志。
- 如果标志为 true，跳过槽38的远跳，执行槽39–41：准备并调用 `SL:RequestGetAllMailItems()`。
- 槽42 Opcode388将自动领取分支跳过至槽55之后，故本轮不会继续执行删除已读邮件分支。
- 如果标志为 false（没有符合条件的邮件，或迭代结束），槽37不跳过槽38；槽38跳至槽43。
- 槽43–46融合/调用链读取 `SL:GetMetaValue("MAIL_HAVE_DEL_ITEM")`。
- 槽47 Opcode358检查该标志；为 false 时槽48跳过删除调用，直接跳至槽55之后；为 true 时跳过槽48，进入槽49–51，调用 `SL:RequestDelReadMail()`。
- 槽52–54准备并调用 `SL:RequestMailList()`，在删除请求之后刷新邮件列表。

因此本轮的优先顺序是：
1. 发现符合领取条件的邮件：调用 `RequestGetAllMailItems()`，本轮跳过删除已读邮件检查。
2. 没有符合领取条件的邮件：检查 `MAIL_HAVE_DEL_ITEM`。
3. 删除标志为真：先调用 `RequestDelReadMail()`，再调用 `RequestMailList()`。
4. 删除标志为假：不发删除请求，也不在此分支请求邮件列表。

## 四、与唯一正式版的差异

唯一正式版当前 `RunMailMaintenance_11_16()` 的实际逻辑为：

- 读取 MAIL_LIST；
- 若不是 table，则局部替换为空表；
- 无条件调用 `SL:RequestMailList()`；
- 若 `MAIL_HAVE_DEL_ITEM` 为真，调用 `SL:RequestDelReadMail()`；
- 返回 mailList。

逐项差异：

1. 正式版无条件请求 MAIL_LIST；原版只在列表不存在或为空时请求，非空时进入迭代。
2. 正式版没有逐封扫描 `MAIL_LIST` 的邮件对象。
3. 正式版没有检查 `sItem` 是否存在/非空。
4. 正式版没有检查 `btRecvFlag == 0`。
5. 正式版没有调用 `SL:RequestGetAllMailItems()`。
6. 正式版在同一次维护调用中先请求列表再检查删除标志；原版的删除分支仅在没有符合领取条件的邮件时执行，并在删除请求之后再次请求邮件列表。

正式版源码中 `RequestGetAllMailItems` 当前未出现。此前“暂不盲领”的保守实现与本次恢复出的原版分支不一致；这是一项明确的待修复差异，不代表可以未经测试直接修改唯一正式版。
