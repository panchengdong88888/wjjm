# 7.48 更正：root/52/23邮件分支核验记录撤回（2026-11-27）

## 更正原因
上一版7.48把定点提取JSON中的`a`字段误当成解释器opcode，进而把操作数388误判为Opcode388跳转、把槽位1–54按错误的槽边界模拟。该解析口径错误，上一版据此写出的邮件入口分流、槽43–54不可达、RequestMailList/RequestDelReadMail差异结论全部撤回，不得引用为有效结论。

## 原始指令字段的正确含义
直接读取11.16原版`F()`解释器分派器：
```lua
K=W[O]
L=K[1]
```
解释器用`K[1]`作为分派opcode；`K[2]`、`K[3]`、`K[4]`等才是操作数。定点提取JSON对应字段为：
- `opcode` = K[1]，真实分派opcode。
- `a` = K[2]。
- `b` = K[3]。
- `c` = K[4]。
- `d` = K[5]（若存在）。

例如root/52/23槽6的记录为`opcode=66, a=388, b=0, c=11`，真实分派码是66；388是寄存器操作数，不是跳转opcode。Opcode66在原版F()中是多槽融合模板，必须连同其消费的后续物理槽一起解释，不能把后续槽当作独立可执行指令。

## 处理决定
1. 撤回上一版7.48中所有基于`a`字段作为opcode的解释和控制流结论。
2. 不据此修改`RunMailMaintenance_11_16`，不创建实机测试文件。
3. 从原版F()分派器逐一还原槽位融合模板，明确每个opcode消费的后续物理槽数后，再重建root/52/23槽1–54的真实执行流。
4. 后续记录必须同时列出`opcode`与操作数A/B/C/D，禁止把寄存器操作数当作opcode。
