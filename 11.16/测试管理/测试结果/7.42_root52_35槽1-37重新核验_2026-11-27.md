## 可读逻辑恢复

按上述寄存器流，root/52/35的可读行为为：

```lua
local userID = SL:GetMetaValue("USER_ID")

if userID then
    local npcData = string.format(
        '{"UserID":"%s","index":15}',
        tostring(userID)
    )

    H[0].powerRefreshing = true

    LuaSendMsg(
        global.MsgType.MSG_CS_NPC_CLICK,
        0, 0, 0, 0,
        npcData,
        string.len(npcData)
    )

    SL:ScheduleOnce(function()
        H[0].powerRefreshing = false
    end, 3)
end
```

其中H[0]是本函数捕获的状态表代理槽；上面的伪代码仅用H[0]标记捕获来源，不能直接把H[0]当成已经确认的Lua变量名。

## 当前确认结论

1. root/52/35槽1–37的真实控制流已经闭合；USER_ID为真时执行NPC点击消息与ScheduleOnce注册，USER_ID为假时直接结束。
2. 槽4没有nil调用；此前槽4 nil调用的静态结论撤回。
3. NPC点击消息使用`global.MsgType.MSG_CS_NPC_CLICK`，数据为UserID及index=15的JSON，后面跟随四个0、JSON文本和文本长度。
4. 发送前把捕获状态表的`powerRefreshing`设为true；3秒后由子闭包将同一捕获状态表字段设为false。
5. 槽31–36使用的是`SL:ScheduleOnce(callback,3)`，不是`SL:Schedule`。
6. G55实机测试的是两个独立`SL:Schedule`任务的异常隔离；它没有直接测试`ScheduleOnce`，也没有替代本次字节码核验。
