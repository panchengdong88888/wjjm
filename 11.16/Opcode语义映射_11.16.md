## 指令记录格式纠正（2026-11-18）

根据原始文件中的`S()`原型解析函数，物理指令记录格式为：

1. 每条物理记录先读1字节标记`H()`。
2. 仅当标记最低位为0时，才继续读取字段；标记最低位为1时，该物理位置没有指令负载。
3. 标记的第2–3位决定操作数模式，第4–6位决定常量替换标志。
4. 随后通过`Z()`读取16位分派值（解释器直接将其作为`K[1]`），再读取A/B字段，并按模式读取C/D字段；`Z()`对两个字节分别异或0x17后按小端组合。
5. 常量标志的第1、2、3位分别决定A、B、C是否从常量表替换。
6. 因此，标记字节不能当作Opcode；也不能把指令头简单按1字节Opcode读取。

本项目已有的`重点原型指令记录.json`保存了root/3、root/7、root/8、root/9、root/20、root/23、root/80的Opcode及操作数记录，源文件SHA与只读原版一致。上一轮对root/52三个闭包的临时单字节提取结果已撤回，不作为证据。

## 物理指令槽位与跳转索引：S()解析器证据（2026-11-18）

重新检查原始S()完整实现后确认：`for V=1,O() do ... E[V]=K end`中的V是物理指令槽位；当marker最低位为1时，该槽位不写入E，形成空洞。解释器F()按`K=W[O]`取指，并由跳转Opcode直接设置`O=K[3]`。因此，跳转操作数指向W/E的物理槽位编号，而不是过滤空洞后JSON数组中的第几个有效指令。

## 检查点378：S()原始指令解码格式确认（2026-11-22）

从只读原版 `MainLeftBottom 11.16原版.lua` 中定位到 `local function S()`，其指令解码核心为：

```lua
local K=H()
if N(K,1,1)==0 then
  local W=N(K,2,3)
  local Y=N(K,4,6)
  local K={Z(),Z(),nil,nil}
  if W==0 then K[3]=Z();K[4]=Z()
  elseif W==1 then K[3]=O()
  elseif W==2 then K[3]=O()-65536
  elseif W==3 then K[3]=O()-65536;K[4]=Z() end
  if N(Y,1,1)==1 then K[2]=L[K[2]] end
  if N(Y,2,2)==1 then K[3]=L[K[3]] end
  if N(Y,3,3)==1 then K[4]=L[K[4]] end
  E[V]=K
end
```

### 已确认的解码规则
- 每个候选指令先读一个H()标志字节；最低位为1时该槽不写入E指令表，最低位为0时才解码指令。
- 标志字节第2–3位决定K[3]/K[4]的编码形式：00=两个Z()值；01=K[3]读O()；10=K[3]读O()-65536；11=K[3]读O()-65536且K[4]读Z()。
- 标志字节第4、5、6位分别控制K[2]、K[3]、K[4]是否通过常量池L索引替换。
- 最终执行器F()收到的指令元组只有四个位置：K[1]为opcode，K[2]为A，K[3]、K[4]为按标志字节解码的可选操作数。未解码的操作数位置为nil。
