### 2. 槽507：a=208，b=19，c=7，d=1

由于槽482已创建空表，且槽483–506负责建立七个配置子表，当前可闭合的结果是：


## 三、槽672–675的执行入口与N[19]使用

### 槽672：a=188，b=29，c="ipairs"

原始F()中分派值188的对应分支先执行：

```lua
N[K[2]] = Z[K[3]]
O = O + 1
K = W[O]
N[K[2]] = N[K[3]]
```

所以：

- 槽672将常量表中的 `ipairs` 函数装入 `N[29]`。
- 该分支融合消费槽673；槽673的 `b=30,c=19`，执行 `N[30] = N[19]`。
- 槽673不是独立分派入口。

### 槽674：a=386，b=29，c=30，d=31

原始F()中分派值386执行函数调用并收集多个返回值：

```lua
local results = { N[K[2]](Y(N, K[2] + 1, K[3])) }
for i = K[2], K[4] do
    N[i] = results[i - K[2] + 1]
end
```

代入槽674操作数：

- 调用目标：`N[29]`，即 `ipairs`。
- 参数：`N[30]`，即 `N[19]`。
- 返回值写入：`N[29]`、`N[30]`、`N[31]`。

等价调用为：

```lua
N[29], N[30], N[31] = ipairs(N[19])
```

该分支内部不修改O，正常循环尾部递增后进入槽675。

### 槽675：a=388，b=0，c=682，d=nil

这是本检查点发现的关键纠正。

原始F()对分派值388的分支是upvalue/闭包捕获状态处理及PC设置：

- 只有 `K[2] > 0` 才执行捕获映射调整。
- 本槽 `K[2]=0`，所以捕获映射循环不执行。
- 随后执行 `O=K[3]`，即 `O=682`。
- VM循环体末尾统一执行 `O=O+1`，所以实际下一执行入口为槽683，槽682被跳过。

**槽675不是闭包创建分支。** 真正创建闭包的逻辑位于分派值大于388的后续分支，其中才会使用K[4]作为捕获数量并执行捕获描述符循环。因此本槽K[4]=nil不会触发此前推测的 `for U=0,K[4]-1` nil上界错误。

## 四、槽672是否可达

槽667–671逐条核对：

- 槽668：分派值243，`N[0]=N[26]`。

槽672融合消费槽673后，槽674调用 `ipairs(N[19])`；槽674不改变PC，故槽675正常到达。槽675再设置跳转位置，实际下一执行槽为683。

## 五、本检查点结论

1. `N[19]`在槽482初始化为空表。
2. 槽483–506构建七个按钮配置子表；槽507把N20–N26重建为N19数组。
3. 槽546将该数组复制到N0。
4. 槽558只初始化N25，操作数d=19在该分派分支中未使用。
5. 槽632的19是N26的表字段键，不是N19寄存器读取。
6. 槽672/673准备 `ipairs(N[19])`，槽674实际执行该调用并收集三个返回值。
7. 槽675是PC跳转，不是闭包创建；下一执行入口为槽683，槽682跳过。
8. 槽672入口已从槽667–671的顺序赋值路径闭合。更早的槽667入口如何由前段状态到达，以及槽683之后完整迭代体的控制流，留待下一检查点继续确认。
