## 4. 身份断言与nil安全顺序

已检查当前根装配区的关键断言：

- rootSource缺失时rootModule为nil，随后先执行`type(rootModule) == "table"`断言，再访问根表字段。
- a/b/z/timerState的字段读取发生在rootModule类型断言之后。
- T[14..22]每个cell先做table类型检查，再做对象唯一性检查。
- 每个root直接闭包均先通过`requireRecoveredClosure`函数类型检查，再进行关键身份比较或字段挂接；58个必需闭包保护覆盖情况沿用检查点275。
- blacklistState先检查table类型，后检查其字段。
- opaquePairTable先检查外层table类型，再访问长度和子表元素。
- PC275、PC389读取出的模块对象均在字段写入前做table类型检查。

未发现因nil值参与相等比较而绕过函数必需性检查的新增问题。

## 5. 保留的环境读取表达差异（待确认，不擅自改写）

原始VM Dump中：
- PC275：`[146,137,37,"MainLeftBottom",null]`
- PC389：`[82,137,59,"MainLeftBottom",null]`

两处均为OP_137读取全局名`MainLeftBottom`。机器状态及根源码注释将其描述为当前chunk环境`_ENV.MainLeftBottom`读取；但主恢复适配代码目前写成`_G.MainLeftBottom`。

在默认Lua环境中`_ENV`通常指向全局环境表且`_G`指向该表，但仓库尚无证据证明目标宿主加载时二者必然是同一对象。因此：
- 不能把当前`_G.MainLeftBottom`写法称为已逐字恢复的原始表达式。
- 暂不擅自把它改成`_ENV.MainLeftBottom`或裸全局名，以免在目标环境语义未闭合时改变适配器行为。
- 主恢复文件应明确标注这是默认全局环境假设下的恢复适配表达，环境对象身份仍待验证。
