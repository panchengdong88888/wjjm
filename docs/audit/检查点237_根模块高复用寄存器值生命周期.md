## 关键新结论：GetStorageItemData回调是PrintLog

- root PC43创建`root.children[16] PrintLog`并写入父T[4]。
- root PC72创建`root.children[1] GetStorageItemData`并通过OP_387捕获同一T[4] live cell。
- PC43至PC72之间没有对T[4]的直接覆盖。
- 因此GetStorageItemData传入的提示回调可确定为PrintLog，不再保留未知notify身份。
- 已同步`MainLeftBottom_恢复源码.lua`和`短函数草稿_第五十六批.lua`，工厂参数由`notify`改为`printLog`。

## 其他重点

1. T[0]不是最初的模块根表：PC1创建模块表并PC2导出后，PC3把T[0]覆写为a配置表；所有捕获点均看到a表。
2. T[1]多次复用，最终PC30的b表才是闭包捕获值；早期Blocklist/SendHookList/RecvHookList均已写入a表字段。
3. T[2]/T[3]最初的1.0/9.0先用于Blocklist，随后分别覆写为z状态表和timer-state表。
4. T[37]在PC212-PC270作为临时闭包寄存器反复复用；真正被UseItemByIndex和BlacklistPlayerDetection捕获的是PC282构造的单元素物品名称数组。
5. T[41]是MainLeftBottom.blacklist所引用的共享状态表；所有闭包通过live cell访问同一表。
6. T[57]先是八向数值表中的{1,1}子表，随后成为onDamageMsg，再被InstallDamageHook覆盖。PC368/370捕获的是InstallDamageHook；onDamageMsg仍保留在MainLeftBottom.onDamageMsg字段。
